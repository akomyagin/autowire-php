# AutowirePHP

Framework-agnostic PHP DI-контейнер с автовайрингом на базе Reflection API.

Контейнер строит граф зависимостей сам: читает конструктор через Reflection,
разбирает type-hint'ы параметров и рекурсивно создаёт зависимости — без ручной
регистрации каждого класса. Никаких внешних сервисов, БД или Docker: чистая
composer-библиотека.

> Learning-проект (первый на чистом PHP в портфеле). Главная техническая задача —
> детект циклических зависимостей **через интерфейсы** при ленивом резолвинге.
> Не production-фреймворк; экономика не оценивается.

## Статус

MVP реализован: ручные биндинги, reflection-based автовайринг конструктора,
детект циклических зависимостей через интерфейсы, lifecycle-контроль
(singleton/transient), edge cases конструктора (nullable, union, variadic).
После MVP добавлены конфигурация резолвинга атрибутами `#[Inject]` и
`#[Singleton]`, опциональная компиляция графа в кешируемый план резолвинга
(см. «Compiled-режим» ниже) и ленивый прокси-резолвинг тяжёлых сервисов
(см. «Ленивый прокси-резолвинг» ниже; требует PHP 8.4).

Поддерживаемые PSR:

| PSR | Как поддержан |
|---|---|
| **PSR-4** | Автозагрузка `AutowirePHP\` из `src/` |
| **PSR-11** | `Container implements Psr\Container\ContainerInterface`; исключения совместимы с `ContainerExceptionInterface` |
| **PSR-12** | Стиль кода, проверяется `composer lint` |
| **PSR-3** | Опциональный логгер резолвинга (второй аргумент — см. ниже), уровень `debug` |
| **PSR-14** | Опциональный диспетчер событий резолвинга |
| **PSR-6 / PSR-16** | Опциональный кеш скомпилированного плана резолвинга (третий аргумент — см. «Compiled-режим») |

Логгер, диспетчер и кеш необязательны: `new Container()` работает как прежде.

```php
$container = new Container($logger, $dispatcher, $cache);
```

События (`AutowirePHP\Event\`) предназначены **только для наблюдения** —
слушатель не может подменить создаваемый объект:

| Событие | Когда |
|---|---|
| `ResolutionRequested` | На каждый `get()`, включая попадание в кеш |
| `ServiceResolved` | Успех; поле `fromCache` различает сборку и кеш |
| `ResolutionFailed` | Провал кадра, перед пробросом исключения |

Каждому `ResolutionRequested` соответствует ровно одно терминальное событие с
теми же `id` и `depth`. Слушатель не должен бросать исключения: если он всё же
бросит, контейнер не даст ему переписать исход резолвинга — на успешном пути
провал слушателя приходит как `ListenerException`, на пути провала побеждает
исходное исключение резолвинга.

## Compiled-режим (PSR-6 / PSR-16)

Передача PSR-6-пула (`CacheItemPoolInterface`) или PSR-16-кеша
(`CacheInterface`) третьим аргументом конструктора включает компиляцию графа —
никакого отдельного флага нет:

```php
$container = new Container(cache: $anyPsr6PoolOrPsr16Cache);
```

Граф зависимостей обходится рефлексией один раз, план резолвинга сохраняется в
кеш, и последующие `get()` строят объекты по плану без повторного обхода графа
рефлексией. Публичный контракт один на оба режима: те же объекты, тот же поток
исключений, та же последовательность PSR-14-событий и PSR-3-записей
резолвинга, та же идентичность shared-инстансов. Разница — скорость и
дополнительные debug-записи о самом кеше.

**Что попадает в кеш:** только план — чистый массив без единого объекта.
Инстансы сервисов не кешируются никогда. Значения по умолчанию не запекаются
и при компиляции не вычисляются вовсе: план несёт ссылку на параметр (класс +
позиция), а вычисление откладывается до сборки — оно происходит ровно в тот
момент и ровно столько раз, сколько на runtime-пути. Поэтому
new-in-initializer-дефолт остаётся свежим объектом на каждую сборку (transient
не превращается в общий), а дефолт за успешной пробой не вычисляется никогда.
Скалярные и enum-результаты после первого вычисления мемоизируются в памяти
экземпляра контейнера — для них повторное вычисление неотличимо. Мемо не
переживает `new Container(...)`, поэтому в схеме «процесс на запрос» выигрыша
от него нет.

**Инвалидация** — по фактам, без TTL (`expiresAfter()`/`$ttl` не выставляются
никогда):

- хеш карты биндингов/синглтонов участвует в ключе кеша: изменённая
  конфигурация — другой ключ, чужая запись не переиспользуется;
- манифест (`mtime` + `size`) всех файлов классов, чью рефлексию читал
  компилятор — включая родителя, объявившего конструктор, и трейты —
  сверяется один раз при загрузке плана в процесс; расхождение — тихая
  перекомпиляция с debug-записью о причине;
- payload с чужим версионным штампом или нечитаемой структурой молча
  отбрасывается и перекомпилируется.

Отказ кеш-драйвера не ломает резолвинг: любой сбой перехватывается,
логируется на уровне `debug` и деградирует к runtime-reflection.

**Кеш плана обязан быть доверенным хранилищем.** План — это инструкция «какой
класс построить и с какими аргументами», и контейнер ей доверяет: тот, кто может
писать в кеш плана, может подменить построенный класс и заставить вычислить
дефолтное выражение чужого класса. Формат проверяется на структурную
корректность, но это защита от испорченной записи, а не от враждебной:
`class_exists()` перед `new` атакующего не останавливает и создавать видимость
защиты не должен. Практический вывод: не отдавайте под план кеш-бэкенд, куда
пишет кто-то ещё (общий Redis без префикса, каталог с правами на запись
для веб-процесса). Отдельный namespace/пул под план закрывает вопрос.

**Оговорки.** План обязан переживать `serialize()` — это планка PSR-6/PSR-16.
Фактически payload состоит только из строк, чисел и `null`, поэтому переживает
и JSON-round-trip, но контрактом это не является. Гранулярность
`mtime` (1 секунда на части ФС) закрыта сравнением размера файла лишь
частично.

**Цифры** (`composer bench`, PHP 8.3, слоистый граф из 35 классов с
интерфейсными биндингами, синглтонами, nullable- и union-параметрами; медианы):

| Замер | Медиана |
|---|---|
| runtime-reflection `get()` корня | ~265 µs |
| compiled `get()` корня, steady state | ~177 µs (~1.5x) |
| Первый `get()` на холодном кеше: компиляция + запись + сборка | ~720 µs |
| Первый `get()` на тёплом кеше: загрузка + валидация манифеста + сборка | ~640 µs |

Замер честный, поэтому две оговорки. Первая: контейнеры работали **без логгера
и диспетчера** — с наблюдателями относительный выигрыш меньше, их стоимость
одинакова в обоих режимах. Вторая: выигрыш скромнее теоретического сознательно —
compiled-путь сохраняет полный паритет наблюдаемости, то есть каждая зависимость
проходит полный кадр `get()` с событиями, логами и детектом циклов, а не
схлопывается в плоский список `new`. Первая компиляция стоит примерно три
runtime-резолва и происходит как побочный эффект первого `get()` — отдельного
`warmup()` в API нет.

## Ленивый прокси-резолвинг (PHP 8.4)

`lazy($id)` возвращает нативный ленивый прокси PHP 8.4
(`ReflectionClass::newLazyProxy()`): объект отдаётся немедленно, а реальный
резолвинг — рефлексия, конструктор, зависимости — происходит при первом
обращении к свойству или методу. Для потребителя прокси неотличим от
настоящего объекта: `instanceof` держится и по конкретному классу, и по его
интерфейсам, явного `unwrap()` нет. Классы с readonly promoted-свойствами
поддержаны без оговорок — их заполняет обычный конструктор. Обычный `get()`
как строил сразу, так и строит: лень — опциональный режим поверх, не замена.

```php
$service = $container->lazy(HeavyService::class); // граф ещё не построен
$service->run(); // первое обращение строит граф обычным get()-кадром
```

- Ошибки **выбора класса** (несуществующий тип, интерфейс без биндинга,
  не-instantiable класс) бросаются сразу из `lazy()`; ошибки **построения**
  (провал конструктора, неразрешимая зависимость) вылетают из первого
  обращения к прокси — как есть, без обёртки.
- События PSR-14 и записи PSR-3 резолвинга смещены вместе с резолвингом: они
  происходят внутри отложенного кадра при первом обращении, не при вызове
  `lazy()`. Нетронутый прокси не диспатчит ничего; сам `lazy()` пишет одну
  debug-запись о факте откладывания.
- Повторное касание того же прокси во время его инициализации — цикл:
  контейнер сообщает `CircularDependencyException` с читаемой цепочкой
  (нативный PHP `Error` сохраняется в `previous`), а не роняет невнятную
  ошибку про неинициализированное свойство.
- Лень ортогональна компиляции: на compiled-контейнере отложенный кадр строит
  объект по плану, `lazy()` планы не инвалидирует.

## Требования

- PHP >= 8.4
- Composer 2

## Установка

```bash
composer require akomyagin/autowire-php
```

## Пример

```php
use AutowirePHP\Container;

interface ReportStorage {}
final class FileStorage implements ReportStorage {}

final class ReportService
{
    public function __construct(private ReportStorage $storage) {}
}

$container = new Container();
$container->bind(ReportStorage::class, FileStorage::class);

// Автовайринг: контейнер сам увидит, что ReportService просит ReportStorage,
// развернёт биндинг в FileStorage и соберёт весь граф.
$service = $container->get(ReportService::class);
```
